# 《世界模型与具身智能》编写与审查执行流程

> 状态：执行基线 v1
> 适用范围：正文、实验代码、结果、图表、引用、在线案例卡与发布产物
> 关联文档：[书籍设计方案 v0.6](./世界模型与具身智能_书籍设计方案-v0_6.md)

## 1. 目标

本流程把书籍设计方案转换为可持续执行的写作与工程计划。最终交付物不是孤立的正文，而是可以互相追溯的五类资产：

1. 概念与方法正文；
2. 可运行实验代码；
3. 锁定环境下的结果与失败样例；
4. 可追溯的图表；
5. 引用、证据和复现记录。

总体流程为：

```text
PRD
→ 可执行规格
→ 纵向样章
→ 实验骨架
→ 分批章节开发
→ 代码与结果驱动图表
→ 内容/代码/一致性/教学审查
→ 冷环境复现
→ 在线版本发布
→ 案例卡和研究雷达持续更新
```

## 2. 核心原则

### 2.1 不先写完全文再补代码

原理、历史和概念边界可以先起草；涉及性能、资源、效果、失败模式和方法比较的结论，必须由实际实验或明确标注的外部证据支持。不得先写结论，再调整代码或选择性展示结果来配合结论。

### 2.2 规格达到可执行即可冻结

Specs 不追求一次性完美。只要章节模板、术语、证据规则、实验卡、图表规范和质量门禁足以指导一个完整样章，就冻结为执行基线。后续通过版本号和变更记录调整，不静默改变已经发布的规则。

### 2.3 正文、代码、结果和图表共同交付

章节不是一个 Markdown 文件，而是一组同步验收的资产。正文中的指标、表格和结论必须能追溯到结果文件、配置、代码提交和运行环境。

### 2.4 先完成纵向切片，再批量展开

先选择一个代表性章节，完整走通“章节契约—代码—实验—图表—正文—审查—构建”，验证模板和工具链。纵向样章未通过之前，不批量生成其余章节。

### 2.5 失败结果属于正式内容

每个核心实验至少保存一个有解释价值的失败配置、失败轨迹或反例。不能只展示成功结果，也不能把安装成功、模型加载、完成 rollout 和达到功能指标混为一谈。

### 2.6 当前阶段采用 CPU/Docker 优先

当前开发设备没有可用 GPU，因此本阶段的目标是验证接口、数据 schema、前向流程、指标和文档—代码追溯，不追求论文规模训练或最终性能。执行约束如下：

- 默认只运行 CPU smoke、微型训练、单 episode rollout、单元测试和图表生成；
- 需要复杂依赖的实验优先提供 Dockerfile 或 Compose 入口，锁定基础镜像、系统依赖和 Python 环境；
- 必做 smoke 使用随书微型 fixture 或程序化数据，不自动下载完整数据集、大模型权重或大型仿真资产；
- 任何大规模下载、GPU 训练、长时间运行或收费 API 调用，均作为延后验证项，执行前需单独确认；
- 当前设备未运行的 GPU 结果必须标为“待 GPU 验证”，不能根据配置文件或上游 README 宣称本书已复现；
- Docker 负责降低环境差异，但不能替代硬件、驱动和平台兼容性验证。后续 GPU 环境仍需单独执行冷启动和资源实测。

建议为实验提供分层入口：

```text
docker/base       文档构建、测试和公共依赖
docker/cpu        CPU smoke 与微型 fixture
docker/gpu        延后执行的 CUDA/GPU 实验
```

CPU 路径必须能够验证命令、张量形状、数据流和指标计算；它不承担验证样本效率、最终收敛或实时性能的职责。

## 4. 单章标准工作流

每章按以下顺序执行：

1. **章节契约**：写清核心问题、非目标、先修知识、章节依赖和可验证产出。
2. **实验设计**：定义最小实验、标准实验、基线、指标、种子、资源档位和失败条件。
3. **代码骨架**：先建立 README、`experiment-card.json`、可测试模块、测试和 `smoke` 入口；只为适用的训练/外部数据实验增加 `prepare`、`train`、独立 `evaluate/report`，不创建 no-op 步骤。
4. **分级运行**：当前先在 Docker/CPU 中运行 smoke 和微型配置，保存原始日志、环境和失败样例；需要 GPU、大型数据或长时间训练的配置登记为延后验证，不伪造替代结果。
5. **生成图表**：从结果文件生成表格与曲线，不手工重录实验数字。
6. **撰写正文**：根据证据解释结果、反例、适用条件和不确定性。
7. **补齐教学层**：加入 CV 背景桥接、练习、可折叠自检要点、小结和下一章接口；自检给最低合格推理、复核命令/数量级和证据边界，不把开放题写成唯一答案。
8. **执行四类审查**：内容、代码、一致性和教学审查全部通过后才标记完成。

章节状态统一使用：

```text
planned → contracted → smoke → experimented → drafted
→ reviewed → reproducible
```

`drafted` 不能记为完成。`reviewed` 表示正文和当前可执行证据已完成四审，可进入“证据范围受限”的在线发布候选；`reproducible` 另表示章节所要求的目标硬件/数据实验也已冷启动通过。站点是否实际 `published` 由全书发布门禁单独记录，不用发布动作覆盖章节的证据成熟度。

## 6. 章节资产与追溯关系

当前采用以下映射：

```text
docs/part-02-world-models/ch06-rssm.md
labs/track-a-world-model-control/ch06-rssm/
results/ch06/
reviews/ch06-kl-routing-review-2026-09-01.md
```

正文中的实验、图和表使用稳定 ID：

```text
EXP-06-01  实验
FIG-06-03  图
TAB-06-02  表
CLAIM-06-04  关键声明
```

实验卡至少记录：

- 数据名称、版本、许可和校验和；
- 代码 commit、第三方项目 commit 和配置文件；
- 随机种子、硬件、内存、峰值显存、磁盘和耗时；
- 适用的准备、训练、评测和报告命令；纯解析/metadata fixture 明确说明为何没有训练阶段；
- 原始指标、统计方式和失败定义；
- 生成的表格、图片和正文引用位置；
- 论文结果、本书结果和未验证声明的区别。

若章节定义了可复用的模型/策略比较协议，还要在运行前建立独立 benchmark card。它冻结用途与允许/禁止声明、系统角色、数据 split/group/leakage、样本单位、指标方向与实现、统计方法、OOD/拒绝协议、报告粒度和退出条件。单次运行继续写 experiment card 并与 benchmark ID 双向引用，测量值写 result artifact；不得看完结果后静默修改 benchmark card，协议发生实质变化时必须升版本。

不是每个教学 smoke 都需要 benchmark card。只有结果被用于横向比较、准入门禁或反复运行时才建立，避免为满足形式而虚构数据划分、置信区间或 OOD estimator。机器 Schema 证明字段与引用一致，不替代科学有效性审查。

## 7. 四类审查门

### 7.1 内容审查

- 概念、公式和术语与全书契约一致；
- 不混淆世界模型、策略、视频生成器、仿真器和数字孪生；
- 关键研究结论回到原论文、官方代码或数据卡；
- 公司产品能力明确标为供应商声明；
- 事实、解释、推断和作者建议可以区分。

### 7.2 代码与复现审查

- 当前阶段优先验证 Docker/CPU 冷环境，依赖、模型和数据版本已锁定；
- S 档至少有 `smoke/evaluate/report` 合同；训练型实验再要求 `train` 与 `evaluate/report` 分离，解析/metadata fixture 可复用同一确定性脚本；
- CPU smoke 至少验证数据流、前向、损失/指标和单 episode；微型训练结果不外推最终性能；
- 24GB 单卡限制只能在后续 GPU 环境实测，未经实测的章节标为“待 GPU 验证”；
- 安装、加载、rollout、稳定性和功能指标分别报告；
- 失败结果、异常退出和恢复方式有记录。

### 7.3 文档—代码—图表一致性审查

- 正文数字能定位到结果文件和实验 ID；
- 图表由锁定脚本和输入生成；
- 正文描述的超参数与配置一致；
- 表格中的硬件、数据版本、任务和指标可以横向比较；
- 同一术语和符号在不同章节含义一致；
- 删除或改名资产后，不留下失效引用。

### 7.4 教学审查

- 目标读者无需未声明的 RL、机器人或 3D 前置知识；
- 新概念在首次使用前完成桥接；
- 最小实验能够检验本章核心观点，而不只是运行代码；
- 同时展示成功证据、反例和适用边界；
- 练习能检验迁移和判断能力，不只是复制示例。
- manifest 登记覆盖的章节中，每道练习都有同编号自检要点；未覆盖章节明确保持待补，不把局部答案误报为全书完成。

## 8. 图表规范

图表分为两类：

1. 架构图、概念图：保存 Mermaid、SVG 或其他可版本管理的源文件；
2. 实验图、结果表：从结构化结果文件自动生成。

每张图必须保留：

```text
源文件 + 生成命令 + 输入结果 + 导出文件 + 图注 + 来源/许可
```

图注必须说明它是原论文重绘、本书概念抽象、实际代码结构还是实验结果。不得把概念示意图当成代码实现图，也不得手工修改曲线来改善展示效果。

## 9. 自动化质量门禁

每次合并或发布至少检查：

```text
Markdown/Mermaid 严格构建
内部与外部链接
引用键和证据标签
术语与符号
章节模板完整性
实验卡与 benchmark card schema
代码单元测试与 smoke
结果文件存在性
正文数字与实验 ID 映射
图片来源和许可
资源预算与运行环境
```

自动检查通过不等于内容正确；它只负责发现结构和追溯问题，关键技术结论仍需人工审查。

## 10. 章节完成定义

一章只有同时满足以下条件，才能标记为 `reproducible`：

- 章节契约、正文、练习和章节出口完整；第1–21章使用“下一章接口”，第22章使用“全书出口”；
- S 档实验可冷启动运行；M/L1/L2 内容均有明确可选标记；
- 关键结论有外部证据或本书实验支撑；
- 所有正文指标可追溯到结果和配置；
- 图表有源文件、生成命令和来源说明；
- 至少记录一个失败或反例；
- 内容、代码、一致性和教学审查通过；
- 已知限制和未验证声明没有被隐藏。

在当前无 GPU 阶段，完成正文、Docker/CPU smoke 和四类审查的章节最高标为 `reviewed`。只有所需 GPU/大数据实验在目标资源档位完成实测后，才能升级为 `reproducible`。`reviewed` 章节可以进入明确标注证据范围的在线书候选，但未验证性能、资源或部署声明不得作为本书实测结论发布。
